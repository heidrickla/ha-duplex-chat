# Decisions

How duplex-chat works and why, one row per decision.

| Decision | Consequence |
|---|---|
| The broker and its panel run as a Home Assistant add-on. Session adapters run on the machines that host the sessions and connect outbound to the broker. | History and the panel survive any one machine being off. Adapter-to-broker traffic crosses the local network, so every adapter connection authenticates with a per-binding token, and the clients speak plain `http://` to the add-on's port. |
| The add-on lives in `duplex_broker/` with `repository.yaml` at the root; adapters live in `adapters/` and `crates/`. | The repository installs as an add-on repository from its git URL. |
| The Claude sessions to reach are desktop-app sessions, so Claude Code channels, which need an interactive terminal launch with a flag, are not the adapter. | The adapter uses Claude Code's cross-session messaging (`feasibility.md`). |
| A Claude session is woken by posting a fixed line into its own inbox from the MCP server instance running in that session; the message text comes through `bridge_receive`. | No model call wakes a session, and no terminal, hook or flag is needed. |
| The chat surface is the panel in the Home Assistant sidebar, on the owner API; any other client uses the same API with an owner device. | Chat content stays on your own network. No model API tokens are involved: replies come from the sessions' own logins. |
| The Claude and Codex adapter is the `duplex` binary (`crates/duplex`), active in a session only when `~/.duplex-chat/adapter.json` exists. | One binary, no Python on the session's machine. `duplex setup` writes the file and registers the server. |
| A delivery stops being in flight once the session has read it (`consumed`). The Claude adapter releases at read, because Claude Code queues the session's inbox itself. The Codex app-server adapter holds `accepted` until the turn ends. | `INFLIGHT` is `dispatching` and `accepted`. |
| The Codex app-server adapter owns its threads in its own app server, with `workspace-write` and approvals `never`. A message from the owner becomes turn input; a peer message is refused (`failed`). | Approvals cannot be relayed, so none are requested. A command needing more than the sandbox fails rather than waiting on nobody. Peer text never becomes a Codex prompt. |
| Codex desktop tasks join like Claude sessions: the MCP server in the task is the adapter, the task calls `bridge_register` with its `CODEX_THREAD_ID`, and the wake is `codex queue` into that thread. | No always-running process of ours. Codex starts MCP servers with no `CODEX_*` variables and ignores `tools/list_changed`, so the tools are visible from the start. |
| Local config lives in `~/.duplex-chat`, not in AppData. | The Claude and Codex desktop apps are packaged, and each package's AppData writes land in its own store, so a file written from one is invisible to the other. The profile folder is not virtualized. |
| Group modes. Consult: a session asks one question per owner message addressed to it, as a reply to that message; the asked session answers once, to the asker. Collaborate: the owner sets an objective, a turn budget (default 6, at most 12) and a deadline (default 10 minutes, at most 60); every session in the group takes part; a peer message spends a turn, a reply to the group is free; a message repeating its parent is refused. Any stop returns the group to `user_directed`. | Messages carry `root_id` and `depth` from the owner message that started the chain. Enforcement is in the store, so an adapter cannot exceed the grant. A deadline is recorded by a 15 s sweep and before every session post. |
| Wake ladder. The broker owns deadlines and counts; the adapter repeats its fixed wake line when the claim asks; after the re-wakes an unread delivery closes `uncertain` and the queue moves; a session with repeated closures is held with one notice to the owner. Only adapters declaring `rewake` take part. | One unread delivery does not stall a session's queue. The app-server Codex adapter is left out because its `accepted` covers a running turn of up to 30 minutes. A close shows on the owner's message as `uncertain`, and a hold as a message from `Duplex broker`. |
| Adapter push. Adapters hold a WebSocket to the broker and claim when an event names their binding; a 60 s claim backs up a lost nudge; a broker without the stream is polled. Senders see each recipient's last-seen time, and any member reads one message's delivery trail by id. | A nudge carries no content, so message text still reaches a session only through `bridge_receive`. |
| The ChatGPT connector. A ChatGPT conversation is reached through MCP Events: a connector on its own port behind a public HTTPS hostname you provide, OAuth 2.1 with PKCE linked once with the pairing code, a `chatgpt` binding, ID-only signed events, read and acknowledge as separate tools. | ChatGPT connectors take OAuth with PKCE only. The public port serves the connector paths and nothing else; the owner API and adapters stay on the local network. |
| Message envelope, receipts and failure notices. Every message carries its sender, its recipients and the broker's sent time on every surface. The sender gets a read receipt per recipient and a failure notice per recipient whose delivery fails. A failed hand-over is retried once after 2 s, then reported failed. | Receipts do not wake a session sender (each wake is a model turn); they ride in its next receive. A failure notice does wake the sender, since it needs acting on. Webhook retries are (0, 2). An accepted event that starts no run shows only as no read: the ladder's close becomes a failure notice. |
| Adapter versions. The adapter reports its version, its checkout commit, the Claude Code and Codex releases it was built against and the runtime it runs under; the broker keeps it per binding and marks a binding `adapter_behind` when its adapter is older than the newest among active Claude and Codex sessions. `duplex compat check` says when a new release needs reviewing against the adapter. | An older broker ignores the unknown `adapter` field, so either side deploys first. An adapter that sends nothing reads as version 0. Built-in members and the broker carry null. |
| Send modes. A message carries `auto`, `queue`, `steer` or `restart`; an adapter declares what it takes, a binding that declares nothing takes `auto`, and the broker never turns one mode into another: a post any recipient cannot take is refused with 422 `mode_unsupported` naming that recipient and what it supports. `steer` is refused to a session that reports idle, and a session that reports a running turn is handed no `queue` message until it is idle. | Adapters send their turn state to `POST /api/adapter/turn`. |
| Delegated tasks and child questions. A session delegates a task to another with a done-when; the assignee reports a result or asks the requester; a result reported over live child tasks is held until the last child ends; cancelling reaches every descendant; an idle assignee is nudged once; an assignee waiting on approval gets an observed question for the requester that names the kind of wait only. Each task has its own group conversation and every notice is a broker message with a stable client id. | The existing delivery, wake, receipt and ladder machinery carries the notices, and the owner sees each task as a conversation, in the Tasks tab, in `duplex owner tasks` and in `GET /api/tasks`. A task's text carries no authority beyond the owner's grant. |
| Usage-limit resume. An adapter reports a usage-limit failure with its reset time; once the reset passes the broker's sweep posts "Continue where you left off." into the owner's direct conversation with that session, once per limit failure, and not when the session answered since, the work it was doing was cancelled, the session is retired, or the reset is a day old. | The line waits in the session's queue until its adapter registers and claims it. |
| Scheduled sends and the waker. A usage-limit resume is a row of kind `limit_resume` in `scheduled_sends`, so another kind is another `kind` with its fields in `details`. A session whose process is gone cannot claim its queued send, so the broker lists those for a waker service that holds its own token and starts the session; a request is not listed for 15 minutes after a start nor after three failed starts, and the third failure tells the owner once. Each start report carries a `report_id` the waker repeats on a retry; the broker keeps one start per id. | The waker is separate from the broker and optional; a broker that restarts treats every session as live for 90 seconds. `/health` reports the schema and whether migrations and every listener are done. |
| Claim gate, turn reading and task capability. The one-in-flight gate follows the delivery's mode: a delivery taken into a running turn lets an auto, steer or restart head through when the adapter declares steer, and an unconfirmed hand-over still blocks everything. Every claim may carry the adapter's turn reading, applied before the queue hold. A task needs `tasks: true` on both sessions, and a name picks a session by id in its normalized form or by title as typed, in the broker and in `duplex owner` alike. Every delivery is admitted in one place, queued ones again when a session registers. Turn readings carry a sequence number per registration and apply in one transaction under the current lease. | Adapters that declare turn state send it on every claim; one without the task tools is never given a task. |
| The owner's id is stored in the database (schema 13) and the API acts as that stored owner. The owner's display name is an option. | A database from before schema 13 keeps every conversation, membership and delivery visible to its owner. |
| The model member and the ChatGPT connector are optional and generic: any OpenAI-compatible server and any ChatGPT account, titled by options. The model member's actions (tool calls run through Home Assistant's Assist API) are off by default. | Nothing runs a tool without the owner turning actions on; Assist exposure is the boundary. |
| Named services replace a single queue token: each has a name and a token, and its own routes under `/api/service/{name}/`. | A restricted caller can read the active sessions and post status notices in its own direct conversations, and nothing else. |
| `duplex setup`, `duplex owner` and the waker accept only an `http://` broker address, as they carry no TLS stack. | The broker is reached on the local network or through the add-on's port. |
